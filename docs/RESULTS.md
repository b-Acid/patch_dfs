## 2. 与作者设定的偏离

| 项目 | 作者 | 我们 | 原因 | 影响 |
| --- | --- | --- | --- | --- |
| 框架 | PyTorch Lightning 1.x | 纯 PyTorch 逐行移植 | Lightning 1.x 与 Blackwell 需要的 torch ≥ 2.7 不兼容 | 无（语义相同） |
| CIFAR 选择头输出 | 代码 16×16，论文 8×8 | 8×8 | 作者代码与 8×8 mask 不匹配，无法运行 | 按论文 |
| 混合精度 | fp16 | bf16 | 新硬件更稳 | 数值级差异 |
| DIME ViT 前向 | 价值头、预测头各跑一次主干 | 合成一次前向 | 两头共享主干，结果逐元素相同 | 训练快一倍，结果相同 |
| DIME MNIST checkpoint | 监控准确率但 mode=min | mode=max | 作者脚本 bug | 避免选到最差的轮次 |
| DIME 预训练权重 | 保留最后一轮（Lightning 无 checkpoint 回调） | 同作者 | 照搬 | 同作者 |
| MNIST 训练步 | eager | 整步 CUDA graph | 多任务共卡时快 10 倍以上 | 单步逐参数一致（7e-9），随机数流不同 |
| 评测 | 每个预算重新选一遍 | 一次选到最大预算，逐步记录预测 | argmax 选择确定，结果相同 | 无 |

### batch 256（吞吐）

| 模型 | 整图一次 | k=10：作者实现 | k=10：头融合 | k=10：丢 token |
| --- | --- | --- | --- | --- |
| DIME ViT-S/16 | 2444 GFLOPs，39.9 ms | 23× / 23× | 12× / 12× | FLOPs 0.72×，延迟 5.0× |

丢 token 的一次前向按已看块数变化：batch 1 下不管 1 个还是 196 个 token 都是约 4.2 ms（kernel 启动开销主导，与稠密版一样）；batch 256 下 16 个 token 16.7 ms、128 个 token 28.3 ms、197 个 token 39.9 ms，固定开销约 16.7 ms，每多一个 token 约 0.12 ms。

结论：
1. 按作者代码，预算 10 块时 GDFS 是整图一次的 14 倍，DIME 是 23 倍；DIME 把价值头和预测头合成一次前向后是 12 倍，这是不改变模型就能拿到的 2 倍。
2. 丢 token 把 FLOPs 倍数从 12× 压到 0.72×（k=10 时整个选块过程比整图跑一次还少 28%），但单张图延迟一点没降，仍是 12×，因为 ViT 每次前向有约 4 ms 的固定开销，与 token 数无关。
3. 吞吐场景下丢 token 有效：batch 256 时 k=10 的延迟倍数从 12× 降到 5.0×，k=15 从 17× 降到 7.1×。要把 FLOPs 的节省变成单图延迟，得先把每次前向的固定开销压下去（CUDA graph、compile、减少 kernel 数）。
4. GDFS 的 CIFAR 选择头（上采样块）比预测头贵：选择器一次前向是预测器的 1.3 倍，所以 k 次选择的代价里选择头占大头。

补测（空闲 GPU 0，batch 1，丢 token 版）：把一次前向录成 CUDA graph 后，固定开销从约 5–6 ms 降到 0.86 ms（1 个 token）到 1.14 ms（196 个 token），token 数的影响开始可见但仍然很小。即便如此，k=10 要跑 12 次前向，总延迟约 10 ms，仍是整图一次的 9 倍：单图延迟的瓶颈是"每选一块就要串行跑一遍"这个结构本身，稀疏只是省掉了在 batch 1 下本来就不花钱的算术。脚本 scripts/figures/lat_graph_vit.py。

## 6. 单趟前向的动态选块（我们的方法）

延迟 ≈ 前向次数 × 每次前向的固定成本。固定成本在算子融合后仍是 0.5 ms（batch 1）/ 2.2 ms（batch 256），所以串行结构在 batch 1 下最好也是整图一次的 7 倍；要同时省算力和延迟，只能把前向次数降到 1。做法：同一个 ViT-S/16，前 L 层（"看"）照常算全部 197 个 token；用第 L+1 层里 CLS 对 196 块的注意力打分，保留 top-k，其余 196−k 块按注意力加权合成 1 个汇总 token；后 12−L 层（"想"）只算 CLS + 汇总 + k 块。给定 k 形状固定。机制同 EViT（Liang 等，CVPR 2022），这里是把它作为"串行选块的极限情形"来测量。训练：标签交叉熵 + 对稠密 DIME 预测器（整图 0.994）的硬蒸馏各占一半，AdamW 1e-5 余弦，batch 32，60 轮，验证集取 k=5/10/20 平均做早停；k 每个 batch 在 1–30 随机抽，一个模型服务所有预算。每个运行 0.12–0.2 GPU 小时。架构图：results/fig_onepass_architecture.png

### 算力与延迟（k=10，RTX 5060 干净重测；训练在 RTX PRO 5000）

训练与精度在 RTX PRO 5000 上完成；该卡在测延迟时有多个并行任务，读数不可用。下表是 2026-11-26 在空闲 RTX 5060（8 GB，WSL，无其他计算任务）上同一会话重测的结果（`results/latency_logs/master_5060.json`），报告正文用这一组。两张卡不同，绝对毫秒不跨卡比较，只看同一张卡上的相对倍数。

| 方法 | 前向次数 | FLOPs | batch 1 | batch 256 | 准确率 |
| --- | --- | --- | --- | --- | --- |
| 作者代码（eager，每步两次前向） | 23 | 23× | 129.3 ms | 2757 ms | — |
| 头融合（eager） | 12 | 12× | 67.4 ms | 1438 ms | 0.892 |
| 丢 token（eager） | 11 | 0.72× | 82.3 ms | 260.6 ms | 0.852 |
| 丢 token（compiled） | 11 | 0.72× | 8.62 ms | 103.7 ms | 0.852 |
| 单趟 L=2（compiled） | 1 | 0.24× | 0.87 ms | 29.55 ms | 0.917 |
| 单趟 L=4（compiled） | 1 | 0.39× | 1.01 ms | 43.04 ms | 0.949 |
| 整图一次（compiled，参照） | 1 | 1× | 1.18 ms | 100.58 ms | 0.994 |

"整图一次"是同一模型 k=196 的路径，与单趟在同一会话同一张卡上测得。FLOPs 用 FlopCounterMode 实测，9.4 GFLOPs 为整图一次。前向次数按实际推理循环计（含最后一次预测前向）；§4 账本按作者 predict_step 结构记 k+2 次，多算一次 1 个 token 的前向。compiled 与 eager 的最大 logit 偏差约 1.4（L=4，k=10），精度评测仍用 eager。

结论：

1. 同一预算下单趟更准：k=10 时 L=2（0.915）比串行稠密高 2.3 点、比串行丢 token 高 6.3 点；L=4（0.951）与串行最好的惩罚式（9.8 块 0.954）持平。原因是前 L 层看了全部 196 块，这是串行模型在 k=10 时做不到的；所以在"只观察 k 块"的意义上两者不是同一任务，在算力和延迟的意义上才是同一比较。
2. 算力：k=10 时 0.24× 整图一次，是串行丢 token（0.72×）的 1/3、作者代码（23×）的 1/97。
3. 延迟：batch 256 下 29.6 ms = 0.29× 整图一次，比串行丢 token compiled（103.7 ms）快 3.5 倍，比作者代码快 93 倍。batch 1 下 0.87 ms = 0.74× 整图一次，只省 26%：batch 1 下 12 层每层约 98 µs 的固定成本（读权重、启动 kernel）与 token 数无关，整图一次的 1.18 ms 本来就是这个地板；单趟在 batch 1 下的收益被这个地板限制，但仍比串行 compiled（8.62 ms）快 9.9 倍。
4. 看的层数 L 是唯一的旋钮：代价是整图的 L/12，小预算准确率从 L=1 到 4 上升很快，L=6 饱和。
5. 机制不新（EViT、DynamicViT、A-ViT），这里的贡献是同一模型、同一数据、同一卡上把串行 / 每步多块 / 单趟的"前向次数 × 固定成本"分解测出来。
